# Scientific data lifecycle — M3.3

Source acquisition → hash verification → parsing → raw draft storage → raw sealing → semantic reconciliation → quality review → analytical eligibility → result draft → validate/seal/approve/publish → current or historical reads.

Only acquisition, CSV parsing/filesystem artifacts and documentary reconciliation exist today. No database lifecycle is implemented. The [binding contract](postgresql_schema_proposal.md#binding-integrity-contract) is authoritative for every transition.

1. Preserve supplied original filenames, aliases, unknown retrieval dates/URLs and verified hashes. New hashes are new artifacts, not overwrite operations.
2. Create a draft parsing aggregate; validate exact headers, counts, rows/cells and archived output. Seal atomically. Later attachments are forbidden, even though all rows are append-only.
3. Propose interpretations and evidence children. Seal each annotation before approval; approval pins its variable-definition review and source parse seal. Evidence supplements require a new annotation revision.
4. Create documented segments, typed components and condition drafts. Seal and approve, pinning every known component's annotation and identity-link decisions. Unknown components remain explicit and cannot satisfy required known protocol conditions.
5. Register and seal the exact protocol requirements/unit rules. Use the N2 six-row truth table with and without condition-role requirements. No such roles plus not_required/not_applicable on every input permits empty ResultCondition; input segments must still be documented. Active policies require matching input annotation/variable components in the same test/segment. Declared condition roles remain required independently. Missing required evidence or decisions fails closed.
6. Build the result draft and all members. In one SERIALIZABLE publication transaction validate N2, seal the result, capture the complete N1 observation/link/issue sets in ApprovalDependency, and create the mandatory approved result review with complete ordinary dependencies, policy version and zero-unresolved attestation. Seal that review using canonical-json-v2 and append the publication event. Deferred publication checks validate exact set equality before commit, including later writes in the same transaction. Failure commits no publication. No seal alone grants analytical permission.
7. Every consumption evaluates CanConsume in a fresh transaction, including ApplicabilityCurrent: exact current observation/link/issue membership and head/seal pointers equal the pinned snapshot. New links (including unreviewed), new issues (including info), any changed head/seal, withdrawn eligibility or revoked approval/publication blocks current use. Historical negative or absent heads are scope facts, not permission edges. No cache or base-table read is an alternate permission source.
8. Historical auditors read only pinned sealed applicability/member/decision sets, including non-selected identity links and explicit missing review/seal facts; they never enumerate current links to explain the past. Revocation cannot recall already returned data. Applicability changes require complete revalidation: unchanged result contents may receive a successor result approval, fresh snapshot and publication while reusing the content seal; changed content requires a new result identity. An issue's later resolution does not automatically restore an old publication's current permission.
9. Metadata changes create reviewed full-snapshot MetadataRevision rows. Source registrations remain immutable. New ScientificVariable versions do not silently replace old annotation/protocol references.

All revision chains use exact predecessor IDs, same-subject revision+1, uniqueness and common subject locks. SERIALIZABLE retries rerun whole transactions. Every member insertion shares the aggregate parent lock with sealing, including nested unit rules. Future tests in the [remediation log](m3_remediation_log.md) are mandatory before ingestion; no such enforcement tests have run.

Condition eligibility has a separate revision stream per protocol/test/segment. The complete ER inventory draws all 140 declared scoped foreign keys across 33 entities; SQL and diagram remain design artifacts. See the schema contract for the exact decision-head, entry-kind shapes and publication rules.

All applicability-affecting writes acquire the investigation lock before ordered parent/subject locks, as specified in N1. This serializes BASS-II writes conservatively; SERIALIZABLE retries remain necessary, and waiting does not refresh a transaction snapshot. A publication snapshot attests its valid serializable view; a later fresh consumption observes committed changes. The [M3.3 log](m3_3_remediation_log.md) specifies concurrency and policy tests. No database enforcement has been run and no approval of M3 is claimed.
